# Gerenciador de Tarefas (estilo Trello)

Sistema de controle de tarefas em quadro (kanban) com TAGs como colunas e
tarefas como cards arrastáveis. HTML/CSS/JS puro no frontend, PHP no
backend (API REST em JSON) e Firebird como banco de dados.


## 1. Requisitos

- Servidor web com PHP **8.0+** (Apache ou Nginx + PHP-FPM)
- Extensão **pdo_firebird** habilitada no PHP
    - Windows: já vem no instalador oficial do PHP, só descomentar
      `extension=pdo_firebird` no `php.ini`.
    - Linux: costuma exigir compilar o PHP com `--with-pdo-firebird` ou
      instalar um pacote como `php-interbase` / `php8.x-interbase`,
      dependendo da distro.
- Firebird **3.0 ou superior** (o schema usa `GENERATED BY DEFAULT AS
  IDENTITY`, equivalente aos generators, só disponível a partir do 3.0)


## 2. Estrutura de pastas

```
gerenciador-tarefas/
├── index.html          Tela de login (código da empresa + e-mail + senha)
├── home.php             Tela inicial (board + menu lateral) - protegida por sessão no servidor
├── css/style.css
├── js/
│   ├── api.js            Helper de fetch + toasts
│   ├── login.js
│   └── home.js           Board, drag-and-drop, modais
├── api/                  Endpoints PHP (um arquivo por recurso)
├── config/conexao.php    Configuração de acesso ao Firebird (mestre + banco de cada empresa)
├── includes/funcoes.php  Sessão, autenticação, helpers
├── uploads/               Anexos de tarefas e eventos
└── database/
    ├── schema.sql                          Script de criação das tabelas de uma empresa
    └── mestre_schema.sql                    Script do banco mestre (lista de empresas)
```


## 3. Instalação

Este sistema é multi-empresa: existe um banco **mestre** (só a lista
de empresas, ligando o código de acesso ao banco de cada uma) e um
banco **por empresa** (tarefas, tags, usuários — tudo isolado). Se você
só vai usar com uma empresa mesmo, ainda assim precisa dos dois: o
mestre existe só pra resolver "esse código pertence a qual banco".

**Passo 1 — Criar o banco mestre.** Rode `database/mestre_schema.sql`
num banco novo (`MESTRE.FDB`). Ele fica pequeno pra sempre — só cresce
uma linha por empresa cadastrada.

**Passo 2 — Criar o banco da empresa.** Abra o `database/schema.sql`
num cliente Firebird (isql, DBeaver, Flamerobin) e ajuste o `CREATE
DATABASE` no topo do arquivo para o caminho desejado. Rode o script
inteiro — ele já cria as tabelas, as chaves e um usuário administrador
de teste.

**Passo 3 — Ligar as duas coisas.** No `MESTRE.FDB`, registre essa
empresa com um código de 6 caracteres (veja o exemplo de `INSERT` na
seção 4.2 mais abaixo) apontando pro banco do passo 2.

**Passo 4 — Configurar a conexão.** Edite `config/conexao.php` e
ajuste `DB_HOST`, `DB_PATH_MESTRE`, `DB_USER` e `DB_PASS` para o seu
ambiente.

**Passo 5 — Publicar os arquivos.** Copie a pasta inteira para dentro
da raiz do seu servidor web (ex.: `htdocs/gerenciador-tarefas` no
XAMPP, ou um vhost apontando pra essa pasta). Os caminhos usados no
frontend (`api/...`, `css/...`, `js/...`) são relativos, então
funcionam tanto na raiz do site quanto numa subpasta.

**Passo 6 — Testar upload.** Confirme que o usuário do PHP (ex.:
`www-data`) tem permissão de escrita em `uploads/tarefas` e
`uploads/eventos`.

**Passo 7 — Acessar.** Abra `index.html` pelo navegador (via HTTP, não
`file://`, senão os `fetch` para a API não funcionam), e entre com o
código cadastrado no passo 3.

Pra cadastrar empresas **novas** depois dessa primeira, o jeito certo
é usar o **Painel de Suporte** (projeto separado, entregue à parte) —
ele automatiza os passos 2 e 3 (cria o banco e registra o código).


## 4. Acesso inicial

```
Código da empresa: (o que você cadastrou no passo 3 da instalação)
E-mail:            admin@sistema.com
Senha:             123456
```

Recomendo cadastrar seu usuário real e trocar/desativar esse admin de
teste assim que possível (a tela de cadastro de usuário não tem edição
de senha própria ainda — dá pra ajustar direto no banco ou estender o
endpoint `api/usuarios.php`, que já tem o `PUT` pronto pra isso).


### Código da empresa no login: não precisa decorar

Ninguém precisa digitar o código toda vez:

- **Por link**: abrir `http://seu-servidor/gerenciador-tarefas/?empresa=CENTRA`
  já preenche o código no login (o cursor vai direto pro e-mail). É o
  que o Painel de Suporte gera e permite copiar pra repassar ao cliente
  — a empresa pode salvar nos favoritos ou mandar pro time todo.
- **Lembrado no navegador**: depois do primeiro login que deu certo, o
  código fica guardado naquele navegador (`localStorage`) e já vem
  preenchido nas próximas vezes, mesmo sem o link. Se o usuário limpar
  os dados do navegador ou trocar de computador, volta a precisar do
  link (ou do código) uma vez.

O código sozinho não dá acesso a nada — só aponta qual empresa; e-mail
e senha continuam obrigatórios —, então não é informação sensível.


## 4.1. Migração: Arquivamento de tarefas + Histórico/Auditoria

Se você já tem o banco criado a partir de uma versão anterior deste
projeto, rode `database/migracao_arquivamento_historico.sql` no seu
banco existente (não precisa recriar nada). Ele adiciona:

- Os campos `ARQUIVADO` e `DATA_ARQUIVAMENTO` em `TAREFA`
- A tabela `TAREFA_HISTORICO`, com o registro automático de quem criou
  a tarefa, quem moveu entre TAGs (e quando), quem editou e quem
  arquivou/restaurou

Instalações novas já recebem essas tabelas direto pelo `schema.sql`
principal, não precisam rodar a migração separada.

**Arquivar** é diferente de **excluir**: uma tarefa arquivada some do
quadro mas continua existindo e aparecendo nos relatórios (com filtro
próprio de status), podendo ser restaurada a qualquer momento pela
tela "Tarefas Arquivadas" no menu lateral ou pelo botão dentro do
próprio card.

**Eventos** (os comentários que você escreve numa tarefa) agora podem
ser editados, além de criados e excluídos. Eles aparecem numa única
"Linha do Tempo" dentro do card, misturados com as entradas automáticas
do histórico — as automáticas vêm em itálico/cinza e não têm botão de
editar, já que são um registro de auditoria, não uma anotação sua.


## 4.2. Migração: sistema multi-empresa

O sistema passou a suportar várias empresas, cada uma com o **seu
próprio banco de dados** (isolamento real — uma empresa nunca consegue
sequer se conectar acidentalmente no banco de outra). Um projeto
separado, o **Painel de Suporte** (pasta/repositório `suporte-admin`,
entregue à parte), é quem cadastra empresas novas e gera o código de
acesso de cada uma.

**O que muda pra quem já tinha o sistema rodando:**

1. O login agora pede também um **código da empresa** (6 caracteres),
   além de e-mail e senha.
2. `config/conexao.php` foi reestruturado: em vez de um caminho de
   banco fixo, ele resolve dinamicamente qual banco usar a partir do
   código digitado no login. Ajuste só a constante `DB_PATH_MESTRE`
   com o caminho de um banco novo (veja o passo a seguir) — o resto já
   vem pronto.
3. Crie o banco mestre: rode `database/mestre_schema.sql` num banco
   Firebird novo (`MESTRE.FDB`). Ele guarda só a lista de empresas
   (código → caminho do banco) — nenhum dado de tarefa fica nele.
4. Registre o banco que você já tinha como a primeira empresa,
   rodando no MESTRE.FDB recém-criado:

   ```sql
   INSERT INTO EMPRESAS (NOME, CODIGO, CAMINHO_BANCO) VALUES (
       'Minha Empresa',                              -- ajuste o nome
       'CENTRA',                                     -- 6 caracteres, sem O/0/I/1
       'C:\dados\GERENCIADOR_TAREFAS.FDB'             -- o banco que você já tinha
   );
   COMMIT;
   ```

5. A partir daí, toda empresa nova (inclusive a sua, se quiser
   recriar do zero) é cadastrada pelo **Painel de Suporte**, que já
   provisiona o banco automaticamente e gera o código pra você. Veja o
   README desse outro projeto pra instalar e configurar.


## 5. Decisões técnicas (o porquê de cada uma)

- **PDO_FIREBIRD com prepared statements** em vez da extensão
  `interbase` antiga: evita injeção de SQL por padrão, já que os
  valores nunca são concatenados na query.

- **Senha com `password_hash`/`password_verify` (bcrypt)**: o campo
  `SENHA` do seu desenho guarda o hash, nunca o texto puro.

- **Campo `ORDEM` adicionado em `TAREFA`** (não estava no seu desenho
  original): guarda a posição do card dentro da coluna, necessária
  para persistir a ordem depois de um arrasta-e-solta.

- **Regra de visibilidade das tarefas**: seguindo o requisito de
  "vincular usuários" na tarefa, uma tarefa **sem nenhum usuário
  vinculado** fica visível para todos (comportamento de tarefa
  pública/geral); assim que ela tem ao menos um vínculo em
  `TAREFA_USUARIOS`, só quem está vinculado a enxerga no board. Isso
  fica centralizado na consulta de `listarTarefas()` em
  `api/tarefas.php` — dá pra trocar a regra ali se quiser algo
  diferente (ex.: sempre exigir ao menos um vínculo).

- **`ANEXO` guarda o caminho do arquivo em disco**, não um BLOB
  binário no Firebird. Fica mais leve para o banco e mais simples de
  servir depois (link direto via Apache).

- **Atualização parcial em `PUT /api/tarefas.php`**: o endpoint só
  altera os campos que vierem no corpo da requisição, mantendo os
  demais como estão. É o que permite o drag-and-drop mandar só
  `{ id, id_tag }` ao mover um card sem apagar descrição/observação.

- **Soft delete** (`ATIVO = 0`) em `USUARIOS`, `TAG` e `TAREFA`: like
  excluir sem perder o histórico de quem criou o quê.


## 6. Possíveis melhorias futuras

- Edição de usuário existente pela tela (o endpoint já suporta `PUT`,
  falta o botão/modal no frontend)
- Reordenar cards dentro da mesma coluna via drag-and-drop (hoje o
  drag-and-drop move entre colunas; a ordem dentro da coluna só muda
  automaticamente ao criar tarefas novas)
- Exportar o relatório para CSV/PDF
- Paginação na listagem de usuários/relatório para volumes grandes
- Notificação em tempo real quando uma tarefa é movida por outro
  usuário (hoje precisa recarregar a página)
